FuguOracle Spec Review

A critical review of the FuguOracle specification against the Blockstream reference implementations, from five angles: wire compatibility, client compatibility, security, OpenBSD fit, and internal consistency.

Verdict

The cryptographic and wire core of the specification is sound. Every byte-level claim that the review probed matches the upstream server, the libwally C source, and the production Jade client. The review confirmed 34 defects. Five are high severity. Four of the five highs share one root cause: the failure-path taxonomy. Decision D-10 routes every post-decryption failure to HTTP 200 with a junk key. Upstream does not do this. The rule diverges from upstream, contradicts the spec's own 500 rules, and makes the D-12 byte-identical acceptance gate unsatisfiable as written. A junk 200 on set_pin also silently bricks a Jade wallet. The fifth high is a bring-up blocker: the keygen pledge set forbids the chown that the same unit requires. The fix path is narrow. Rescope D-10 and D-12 with human approval. Assign explicit statuses to set_pin and payload-extraction failures. Repair the keygen sandbox. The remaining findings are internal contradictions, client-documentation gaps, and hardening polish.

Scope

The review target is the specification only. The repository holds no implementation code. Every finding names a defect in the spec: a divergence from reference behavior, a security gap in the design, a contradiction, or a material omission.

What held up

A critical review must also state what survived attack. These properties were probed directly against primary sources and empirical execution, and they held:

  • Envelope layout. The parse order and offsets (cke[0:33], counter[33:37], encrypted[37:]) are byte-exact against upstream. The 101-byte minimum equals libwally's effective decrypt floor.
  • Tweak derivation. m = SHA256(HMAC-SHA256(key=cke, msg=counter)) and the BIP341 x-only private tweak with even-Y negation match server.py, libwally, and Jade pinclient.c line for line. The spec's warning that a plain scalar add differs is correct and important.
  • Envelope crypto. Keys split 32/32 from HMAC-SHA512(shared, label); the MAC covers IV‖ct only; the labels match byte for byte with no NUL. Encrypt-then-MAC order matches. Ciphertext splicing across requests fails because the ECDH secret binds cke and the counter through the tweak.
  • Payload and signature. The 97/129-byte forms, the signed message H(cke‖counter‖pin_secret‖entropy), and recid = (sig[0]−27)&3 match libwally exactly. The 96-byte response envelope matches Jade's hard SERVER_REPLY_PAYLOAD_LEN requirement.
  • Storage stack. All three key derivations, the hex-of-SHA256 filenames, the 129-byte version-0x01 record, the 69-byte plaintext, the get_pin thresholds, the wipe values, and set_pin's replay reset match upstream field by field.
  • Blindness. STORE-KEYS-2 is sound: the record key derives from the un-stored pin_pubkey, so disk plus the static key yields no record plaintext.
  • Anti-replay. The strictly-greater, gap-tolerant check is exactly right for Jade's device-global, never-reset counter.
  • Sandbox idiom. The pledge–unveil–repledge sequence in SEC-SANDBOX is canonical and its promise set is sufficient for the CGI program (verified against pledge(2) and libc sources).
  • Simplicity wins. The single global lock plus atomic writes are simpler and more correct than upstream, which has neither. Static linking, the libc primitive choices, and the BUILD_DEPENDS-only packaging are accurate OpenBSD practice.
  • Structure. spec_check.py passes: 39 units, 116 rules, and every anchor, citation, and numeric size claim resolves and verifies.

Findings — wire-protocol compatibility

High The set_pin junk path is wire-incompatible with upstream and silently bricks a Jade wallet

D-10, PROTO-HTTP-8, and OPS-JUNK route every post-decryption failure to HTTP 200 with a junk key. Upstream has no junk path in set_pin: a replay violation, missing entropy, or a corrupt record raises, and Flask returns HTTP 500. Upstream tests pin this as intentional ("Set-pin should fail more overtly"). A Jade cannot detect a junk key on the set flow. It decrypts the envelope, derives the final key from the junk value, persists the wallet under it, and reports success. Every later unlock then fails until the local three-strike counter erases the wallet. A spec-conformant implementation diverges on client-observable paths and violates D-12.

Fix Scope the junk path to get_pin only, exactly as upstream. Specify HTTP 500 for every set_pin failure after envelope decryption. Amend D-10 with human approval. Record the set_pin silent-failure hazard in clients.md.

D-10 · D-12 · PROTO-HTTP-8 · OPS-JUNK-1 · OPS-SET-2 — pindb.py:252–301, flaskserver.py:104–115, test_pinserver.py:569–606, pinclient.c:316–346
High Payload-extraction failures take the junk path per spec but return 500 upstream; the junk formula is uncomputable

Upstream extracts the payload fields outside its junk try-block on both endpoints. A bad payload length, a wrong-length entropy, or a failed signature recovery raises and yields HTTP 500, pinned by upstream unit tests. The spec routes these post-decryption failures to the 200-junk path. The junk formula HMAC(random32, pin_secret) is also uncomputable when the decrypted plaintext is too short to contain pin_secret.

Fix Assign HTTP 500 to payload-length, entropy-length, and signature-recovery failures on both endpoints. Scope OPS-JUNK-1 to failures that occur after successful extraction of pin_secret and pin_pubkey.

PROTO-PAYLOAD-1 · PROTO-PAYLOAD-4 · OPS-JUNK-1 · D-10 · D-12 — pindb.py:106–129, 252–274, test_pindb.py:523–532
Medium Pre-decryption statuses 400/413 diverge from upstream's 500s, and the deviation is unmarked

The spec mandates 400 for malformed JSON, bad base64, and short envelopes, and 413 for bodies over 4096 bytes. Upstream re-raises every parse exception to a Flask 500 and has no body-size limit. Upstream base64 decoding also silently discards non-alphabet characters that the spec rejects. Honest Jade clients never hit these paths. But the spec never marks these statuses as deliberate deviations, so D-12 and TEST-FUZZ-1 fail over these inputs by construction.

Fix List the status and base64 deviations in the OVR-SCOPE deviation table. Scope D-12 acceptance to well-formed requests.

PROTO-HTTP-2 · PROTO-HTTP-3 · D-12 · TEST-FUZZ-1 — flaskserver.py:84–115
Medium No status is assigned to an envelope MAC or decrypt failure; the junk boundary is ambiguous

No rule assigns an HTTP status to a failed envelope tag check, decryption, or unpad. PROTO-HTTP-8 reserves error statuses for failures before envelope decryption, and OPS-JUNK covers failures after decryption. A MAC failure sits in neither bucket. An envelope of 38 to 100 bytes also fails the 101-byte floor with no stated status. Upstream tests pin this failure class to HTTP 500 on both endpoints.

Fix Add a rule: an envelope that fails the length check, the MAC check, or CBC decryption answers status 500. Draw the junk boundary at successful envelope decryption.

PROTO-CRYPTO-3 · PROTO-HTTP-8 · PROTO-ENVELOPE-1 — test_pinserver.py:452–470, lib.py:58–65
Low The JSON request grammar is underspecified; the "recursive-descent scanner" is over-specified

PROTO-HTTP-7 mandates a recursive-descent scanner for a grammar that has no recursion. The rule does not state whether the scanner ignores or rejects extra members, whitespace, member order, duplicate keys, or string escapes. Upstream json.loads accepts all of these. This unspecified surface is where real fuzz divergence will appear.

Fix Specify a minimal linear scanner and the exact accepted grammar: ignore unknown members, require a plain base64 string with no escapes, define whitespace handling.

PROTO-HTTP-7 · D-12 — flaskserver.py:107–109
Low The padding note "always with at least one pad block" is factually wrong

The interop note says libwally always adds at least one pad block on encrypt. Empirical tests with wallycore 1.5.6 show standard PKCS#7 with 1 to 16 pad bytes. A full pad block occurs only for block-aligned plaintext. A literal reading yields wrong ciphertext sizes for the 97- and 129-byte payloads. The correct request envelope sizes are 197 and 229 bytes.

Fix Replace the note: libwally pads PKCS#7 with 1 to 16 bytes. State the exact envelope sizes 197 and 229.

PROTO-CRYPTO-3 · PROTO-CRYPTO-4 — libwally src/aes.c:156–216
Low The lenient-unpad equivalence claim is incomplete; strict EVP unpad diverges on MAC-valid bad-pad input

Libwally's decrypt never fails on invalid padding, while the spec's strict EVP decrypt does. For a MAC-valid ciphertext with bad padding, upstream returns 500 and a spec-conformant service returns a different result. Only a party that holds the derived keys can build this input, so honest clients are unaffected. A D-12 byte-identity test over such vectors still fails.

Fix Extend the interop note to state the divergence. Exclude forged bad-pad vectors from byte-identity testing.

PROTO-CRYPTO-3 · D-12 — libwally src/aes.c:173–178

Findings — spec consistency and process

High D-10's blanket junk mandate is contradicted by the spec's own 500 rules

D-10, PROTO-HTTP-8, and the OPS-JUNK preamble state that every post-decryption failure returns 200 with a junk key. OPS-SET-2 and PROTO-HTTP-4 require 500 for a corrupt record, which is only detectable after decryption. The rules match upstream and the decision does not. PROTO-HTTP-4 applied to get_pin would in turn diverge from upstream, which answers a corrupt record on get_pin with 200-junk, exactly as OPS-GET-2 says. An implementer receives two conflicting normative answers with no precedence rule.

Fix Rewrite D-10 with human approval: scope the junk guarantee to get_pin. Restrict PROTO-HTTP-4's 500 to true I/O errors and the set_pin path. Align PROTO-HTTP-8 and the OPS-JUNK preamble with the same scope.

D-10 · PROTO-HTTP-4 · PROTO-HTTP-8 · OPS-JUNK-1 · OPS-GET-2 · OPS-SET-2
High D-12 byte-identical acceptance and TEST-FUZZ-1 are not executable as written

D-12 requires the same bytes as upstream, given a fixed random source. Upstream has no injectable random seam; it calls os.urandom directly at every draw site. The spec never pins the RNG draw order that determines the bytes. TEST-FUZZ-1 requires an identical status class, but the spec's own 400/413 deviations produce 4xx where upstream produces 5xx for every malformed-body mutation. The acceptance gate cannot pass as specified.

Fix Scope D-12 and TEST-ACCEPT-1 to the decrypted wire bytes of successful and junk responses. Specify the harness (monkey-patched upstream os.urandom) and the exact draw order per operation. Restate TEST-FUZZ-1's oracle as identical accept/junk/real decisions.

D-12 · TEST-ACCEPT-1 · TEST-FUZZ-1 · SEC-RANDOM-2 · OVR-SCOPE
Medium OPS-WIPE-1's in-place overwrite contradicts STORE-ATOMIC-3's universal mkstemp+rename rule

STORE-ATOMIC-3 requires every record write to use mkstemp plus rename. OPS-WIPE-1 requires an in-place overwrite of the record. Both rules use "must", and no carve-out reconciles them. A rename-based wipe writes a fresh inode and never touches the old blocks, which defeats the stated media-recovery purpose. An in-place write is not crash-atomic. The two rules are mutually unsatisfiable for the same operation.

Fix Add an explicit exemption: the wipe opens the existing record file and writes in place (write, fsync, unlink), intentionally non-atomic.

STORE-ATOMIC-3 · OPS-WIPE-1 · OPS-WIPE-2
Medium testing.md misses tests for several load-bearing properties

No test asserts junk-response uniformity in status, envelope length, and headers, which is the actual OPS-JUNK-2 property. No test inspects the pre-unlink record content of the wipe, which is invisible on the wire. No test covers lock serialization or crash atomicity, a stated correction over upstream. No test covers the HTTP status rules or OPS-SET-2's 500. TEST-KAT-1 omits the RNG draw-order determinism that TEST-ACCEPT-1 depends on.

Fix Add a junk-uniformity regress test, a wipe-record file inspection, a lock and torn-write test, HTTP-status tests, and a draw-order determinism vector.

TEST-KAT-1 · TEST-INTEROP-1 · TEST-ACCEPT-1 · OPS-JUNK-2 · STORE-ATOMIC
Low OVR-PURPOSE is registered n-a although it carries four must-rules

STATUS.md marks OVR-PURPOSE as n-a, defined as "no code can implement the unit". The unit contains four bold-lead must-rules. The sibling n-a units contain no rules, so OVR-PURPOSE is the outlier. spec_check.py validates structure only and cannot catch this.

Fix Move OVR-PURPOSE to an open state with a phase, or strip the rule markers.

OVR-PURPOSE · STATUS.md
Low Terminology drift: "PIN proof", the 129-byte "envelope", and the "per client key" counter scope

index.md's "PIN proof" never recurs; the protocol uses pin_secret and sig. OPS-WIPE-1 calls the 129-byte record an "envelope", a term the protocol reserves for the wire envelope. The envelope table says the replay counter is "strictly monotonic per client key" directly under the row that defines cke, but the counter is monotonic per pin_pubkey record. An implementer who binds the counter to cke builds a replay check that never fires, because cke changes on every request.

Fix Say "record" in OPS-WIPE-1. Replace "PIN proof". Change the table cell to "strictly monotonic per pin_pubkey record (see OPS-GET-2)".

PROTO-ENVELOPE · OPS-WIPE-1 · OPS-GET-2
Low OPS-WIPE-1 omits the hash_pin_secret content of the overwrite record

OPS-WIPE-1 specifies aes_key, count, and replay_counter for the pre-unlink overwrite but not the hash_pin_secret field. Upstream keeps the previously stored hash. An implementer must guess the remaining 32 bytes of the plaintext.

Fix State that the overwrite keeps the stored hash_pin_secret, so the full 69-byte plaintext is defined.

OPS-WIPE-1 — pindb.py:229–241
Low Systematic ASD-STE100 deviations: compound rule sentences

Many rules chain two or three instructions in one sentence with "and must", against the project's own one-instruction-per-sentence standard. Examples occur in seven documents. A few passive constructions remain. spec_check.py does not lint sentence structure, so the pattern passes CI.

Fix Split compound rules into numbered sub-sentences, or explicitly permit the pattern in spec/CLAUDE.md.

OPS-GET-2 · OPS-GET-4 · ARCH-STACK-1 · DEPLOY-HTTPD-1 · PROTO-RESPONSE-3

Findings — OpenBSD fit and simplicity

High The keygen pledge set forbids the chown that PROG-KEYGEN-2 requires; bring-up fails

PROG-KEYGEN-2 requires the key file with owner _fuguoracle:_fuguoracle and mode 0400. PROG-KEYGEN-5 pledges only "stdio rpath wpath cpath". pledge(2) gates ownership changes behind the "chown" promise and attribute changes behind "fattr", so the required fchown(2) kills the process. Unveil of only the target directory also blocks getpwnam(3)'s read of /etc/pwd.db. The bring-up procedure aborts, or leaves a root-owned key the CGI cannot read.

Fix Change PROG-KEYGEN-5 to pledge "stdio rpath wpath cpath fattr chown getpw". State the unveil permission string for the target directory.

PROG-KEYGEN-2 · PROG-KEYGEN-5 · DEPLOY-SERVICE-1 — pledge(2)
Medium SEC-LOGGING-1's /var/www/dev/log mechanism is false and conflicts with the sandbox

SEC-LOGGING-1 says the program logs over /var/www/dev/log and that default syslogd creates that socket in the chroot. OpenBSD libc syslog(3) delivers with the sendsyslog(2) syscall, which needs no socket and works in any chroot. Default syslogd creates no such socket. The sandbox grants no "unix" promise and does not unveil the socket path, so a literal socket connection is impossible. Logging via the specified API works anyway under the "stdio" promise; the stated mechanism is wrong.

Fix Rewrite SEC-LOGGING-1 and the ARCH-DEPS row: syslog(3) delivers via sendsyslog(2) under the stdio promise. Drop the /var/www/dev/log requirement.

SEC-LOGGING-1 · ARCH-DEPS · SEC-SANDBOX-2 — syslog(3), sendsyslog(2)
Medium storage.md's relative paths break under slowcgi's chdir and contradict PROG-CGI-4

slowcgi chdirs the CGI child to the script's own directory before execve. STORE-ATOMIC-1 spells the literal call open("pins/.lock", …), and STORE-KEYS-3 gives relative record paths. A literal implementation opens /cgi-bin/pins/… inside the chroot, which the unveil set rejects. PROG-CGI-4 fixes the correct chroot-relative constants. The two normative documents contradict.

Fix Express every storage.md path through the PROG-CGI-4 constants (PINS_DIR "/.lock", PINS_DIR "/<hex>.pin"). State the path convention in one sentence.

STORE-ATOMIC-1 · STORE-KEYS-3 · PROG-CGI-4 · SEC-SANDBOX-3
Medium The CGI environment and error-surface contract is incomplete

PROG-CGI-2's "CONTENT_LENGTH capped at 4096" reads as truncate-and-continue, while PROTO-HTTP-2 requires a 413 rejection. The spec never names the CGI variable that carries the request path under the shipped httpd.conf, which passes the same SCRIPT_FILENAME for all locations. Missing or non-numeric CONTENT_LENGTH has no rule. Error and liveness response bodies and their Content-Type are undefined. SEC-LOGGING-2's outcome classes are never enumerated.

Fix Add rules for CONTENT_LENGTH handling, the routing variable and its expected values, the body shape and Content-Type of error and liveness responses, and the enumerated log outcome classes.

PROG-CGI-1 · PROG-CGI-2 · PROTO-HTTP-2 · PROTO-HTTP-6 · SEC-LOGGING-2
Low The httpd.conf sketch skips "connection max request body" and leaves platform timeouts unstated

The deployment configuration does not set "connection max request body". httpd then forwards bodies up to its 1 MiB default, and the 4096-byte cap rests entirely on the CGI's own check. The spec never mentions the platform timeouts that bound a request. This is defense-in-depth polish.

Fix Add the body cap to the deployment sketch. Note the default slowcgi and httpd timeouts.

DEPLOY-HTTPD-1 · PROTO-HTTP-2 · PROG-CGI-2
Low SEC-MEMORY-2's "cleanup attribute" alternative is not KNF

SEC-MEMORY-2 offers __attribute__((cleanup)) as an alternative to the goto-out discipline. The attribute is a GNU extension that OpenBSD base code does not use, and style(9) does not sanction it. The alternative contradicts D-07's KNF mandate in the same sentence that invokes style(9).

Fix Delete "or a cleanup attribute". Require the single goto-out discipline.

SEC-MEMORY-2 · D-07
Low No key rotation or compromise procedure exists

The spec covers key loss but is silent on rotation and compromise. All storage keys derive from the static key d, so a new key orphans every enrolled record and forces every client to re-enroll. The spec never states this consequence.

Fix Add one rule to deployment.md: rotation is not supported in place. On suspected compromise: generate a new key, clear pins/, re-provision the public key, and have every client set_pin again.

DEPLOY-BACKUP-1 · DEPLOY-BACKUP-3 · STORE-KEYS-1
Low The PLIST omits the /var/www/fuguoracle parent directory

PKG-ORACLE-3 creates only /var/www/fuguoracle/pins/. No rule creates the parent directory that holds both pins/ and the keygen-written private.key. The base mtree ships no such directory, so the package must create and list it, with an owner and mode the _fuguoracle CGI can traverse.

Fix Extend PKG-ORACLE-3: the PLIST also creates /var/www/fuguoracle/ with a stated owner and mode (for example 0710 root:_fuguoracle).

PKG-ORACLE-3 · PROG-KEYGEN-2

Findings — security

Medium OPS-JUNK-2 indistinguishability is broken by conditional fsync'd writes (timing oracle)

OPS-JUNK-2 claims no observable property of the response distinguishes junk-path failures. The mandated paths differ in disk I/O. A missing record, a bad hmac, or a replay performs no write. A wrong PIN and the third-strike wipe perform a full record write, which STORE-ATOMIC-3 turns into a double-fsync operation. Response time separates the paths, and the spec mandates no mitigation. The spec's added durability amplifies a side channel that upstream, which never calls fsync, has in smaller form.

Fix Qualify OPS-JUNK-2 to response content only and add an accepted-risk statement for timing, or require an equivalent dummy fsync'd write on the no-write paths.

OPS-JUNK-2 · OPS-GET-2 · OPS-GET-5 · STORE-ATOMIC-3 · D-10
Medium The attempt counter has no rollback protection; a file restore resets the three-strike limit

The security of the scheme rests on the integrity of the attempt counter. The counter lives inside the record, and the record authenticator is a static function of the key d and the filename. An old copy of a record file stays valid forever. A restore or snapshot silently resets the counter and reopens PIN attempts, and the server cannot detect it. The threat model never mentions this, and the backup guidance invites the exact restore that causes it. Upstream shares the weakness; the spec does not state it as an accepted risk.

Fix Add an explicit risk row: the attempt counter has no rollback resistance against filesystem restore. State it as inherited and accepted, or specify an external monotonic anchor.

OVR-PURPOSE · STORE-KEYS · SEC-THREAT · DEPLOY-BACKUP-2
Low Unbounded record creation via set_pin enables a disk-fill DoS inside the chroot

Any caller who speaks the protocol can mint fresh keypairs and create unlimited 129-byte records. No quota, cap, or eviction exists in the spec or upstream. A full pins/ directory breaks record writes and can starve the shared /var/www filesystem. Unauthenticated set_pin is inherent to the wire protocol, so the remedy is operational.

Fix Add an operational note to deployment.md: place pins/ on a dedicated partition or quota and monitor it. Mark the risk as inherited from upstream.

OPS-SET-4 · D-05 · OVR-RISKS
Low OPS-SET-4's replay-counter reset to 0 reopens a replay window (forced-wipe DoS)

set_pin persists replay_counter = 0, exactly as upstream does. The Jade counter only increments and is never reset. After every PIN change, previously captured wrong-PIN get_pin envelopes replay successfully in increasing counter order. Three replays burn the attempts and force a wipe of the key share. Exploitation needs transport compromise plus captured envelopes, and the behavior is mandatory under D-12, so only documentation can change.

Fix Document the replay-reset window as an accepted, upstream-inherited property: anti-replay protects only between PIN changes.

OPS-SET-4 · OPS-GET-2 · OPS-WIPE-1
Low A fresh random IV per storage write is not explicitly required

The record format carries a 16-byte IV, but no storage rule requires a fresh IV on every write. The storage key is fixed per record, and the record is rewritten on every attempt. A reused IV would reveal, to a disk observer, whether the PIN hash changed. PROTO-CRYPTO-4 states the freshness rule for the envelope path; storage has no equivalent.

Fix Add a storage rule: every record write draws a fresh IV from arc4random_buf(3).

STORE-RECORD · SEC-RANDOM-1 — lib.py:8–11
Low No rule disables core dumps; a crash can spill live secrets

SEC-MEMORY clears secrets on exit paths but never requires disabling core dumps. The process holds the tweaked key, ECDH shared secrets, derived keys, and PIN plaintext in memory. The mandated hand-written parsers run before those secrets clear. A crash can write them to a core file inside the writable chroot.

Fix Add a SEC-MEMORY rule: set RLIMIT_CORE to 0 at startup, before the program reads any request.

SEC-MEMORY-1 · SEC-MEMORY-2 · PROTO-HTTP-7

Findings — client compatibility

Medium The "client keypair derives from the PIN" claim is wrong, and a client built to it loses all brute-force protection Supplemental

clients.md says a conforming client "derives a client keypair from the PIN and its own device secrets". protocol.md repeats the claim. The Jade keypair is a persisted, PIN-independent device key (storage_get_pin_privatekey, generated once). Only pin_secret mixes in the PIN (HMAC(HMAC(pin_privkey, 0x00), pin)). The distinction is load-bearing. A wrong PIN must recover the same public key, so the guess lands on the same record and burns the counter. A client whose keypair depends on the PIN would address a different, missing record on every wrong guess. Each guess would return junk, no counter would increment, and the oracle would grant unlimited online guesses. The spec text prescribes a client design that voids the scheme's core property.

Fix Correct both passages: the client keypair derives from device secrets only, and it must not depend on the PIN. The PIN enters pin_secret alone. State why: a wrong PIN must address the same record.

CLIENT-MODEL · PROTO-PAYLOAD (prose) — pinclient.c:129–139, 350–370. Found in direct review; verified against the firmware source.
Medium clients.md omits that an initialized Jade refuses an oracle public-key change

A Jade with a persisted wallet rejects any update_pinserver call that changes the effective oracle public key. The firmware answers "Cannot update initialized unit". Only URL and certificate changes are allowed on an initialized unit. clients.md states no ordering constraint. An operator who migrates initialized Jades per the spec hits a hard, unexplained failure.

Fix State in clients.md: the Jade accepts a new oracle public key only while no wallet or PIN is persisted. Provision before initial wallet setup, or factory-reset first.

CLIENT-JADE-2 · CLIENT-PROVISION-1 — update_pinserver.c
Low clients.md omits TLS root-certificate provisioning for a custom oracle

Jade's update_pinserver accepts an optional TLS root certificate, which the companion app uses to verify the oracle endpoint. CLIENT-PROVISION-1 lists only the URL and the static public key. The omission bites only private-CA deployments.

Fix Add the optional "certificate" parameter to CLIENT-PROVISION, with a note for private-CA deployments.

CLIENT-PROVISION-1 · CLIENT-JADE-2
Low The TLS-required claim is wrong for the client; the second URL (urlB, onion) is undocumented

CLIENT-PROVISION-2 says TLS is required because the companion app performs the HTTPS call. The client accepts plain http:// URLs, and its default second URL is a plain-HTTP onion address. The Jade emits two URLs (urlA and urlB) to the companion app, and clients.md never mentions the second URL. TLS is a FuguOracle deployment property, not a client or protocol requirement.

Fix Attribute TLS to DEPLOY-HTTPD. Document the optional second URL and the companion app's URL selection.

CLIENT-PROVISION-2 · CLIENT-JADE-2 · DEPLOY-HTTPD
Low The client-appended /get_pin and /set_pin suffixes and the no-trailing-slash rule are unstated

Jade builds each request URL as base plus "/" plus the document name. A provisioned URL with a trailing slash yields "//get_pin". The deployment httpd configuration blocks every path except the three exact locations. The user then sees only a retryable network-error prompt with no cause.

Fix Add a rule to CLIENT-PROVISION: the oracle URL must not end with "/". The client appends "/get_pin" and "/set_pin". Cross-reference from PROTO-HTTP.

CLIENT-PROVISION-1 · PROTO-HTTP · DEPLOY-HTTPD-1

Coverage gaps

The review did not decide everything. These points stay open:

  • The junk-path timing distinguisher was established analytically. No dimension measured actual response-time separability.
  • Companion-app behavior beyond jadepy was not examined: Green/gdk URL selection between urlA and urlB, retry policy, and TLS trust-store behavior.
  • Concurrency under the single global lock (contention, lock-holder crash recovery) was not probed.
  • Storage comparisons used upstream's FileStorage backend only, not the Redis variant.
  • What an older, v1-speaking Jade firmware observes against a v2-only server was not examined.
  • ASD-STE100 compliance was audited by sampling, not by a full lint.

Method

A 13-agent workflow reviewed the specification from six independent dimensions: server crypto compatibility, server behavior and storage, Jade client compatibility, adversarial security, OpenBSD fit and simplicity, and internal consistency. An adversarial verifier re-derived every finding from primary sources and tried to refute it. No finding was refuted; duplicates across dimensions were merged. Verification included empirical execution of wallycore 1.5.6 and an independent re-implementation of the envelope crypto. One supplemental finding (the client-keypair derivation claim) came from a direct manual review of pinclient.c and is marked as such.

The five high-severity findings need a decision change (D-10, D-12), so CLAUDE.md requires human approval before any plan can implement the fixes. The suggested scope: junk responses on get_pin only; explicit 500s for set_pin and pre-extraction failures; acceptance scoped to decrypted wire bytes with a specified harness and draw order; a corrected keygen pledge set.
